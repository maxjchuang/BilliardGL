# BilliardGL 全自动 E2E 控制接口设计

## 目标

为 BilliardGL 构建一套完全由程序驱动的 E2E 接口。测试程序能够启动游戏、执行所有现有用户操作、注入物理测试场景、确定性推进游戏、读取完整状态与事件、生成截图，并在无需人工交互的情况下正常退出。

首期采用基于标准输入输出的 JSON Lines（JSONL）协议。命令协议、游戏控制核心和传输层相互分离，使后续可以增加 Unix Socket、TCP Socket 或 WebSocket，而无需改变命令语义或游戏逻辑。

## 范围

### 包含

- 无头和真实渲染两种自动化模式。
- 原始键盘、鼠标、滚轮和窗口输入。
- 瞄准、力度、击球、摄像机等语义操作。
- 固定步长的确定性物理时间控制。
- 仅在自动化模式开放的测试场景注入。
- 完整游戏状态、游戏事件和截图查询。
- JSONL 标准输入输出传输，以及可扩展传输接口。
- Python 标准驱动器、进程级 E2E 测试和协议文档。

### 不包含

- 首期不实现 Socket 或 WebSocket 服务端。
- 不以操作系统级键鼠注入作为主要自动化手段。
- 不建立第二套独立物理仿真实现。
- 不改变普通玩家模式现有的实时运行体验。

## 架构

### GameRuntime

`GameRuntime` 持有 `GameState`，负责游戏初始化、统一动作分发、固定步长推进、事件收集和状态快照。它不得依赖 OpenGL、GLUT、音频或具体传输方式。

普通交互模式和自动化模式必须共用同一个 `GameRuntime`，从而避免测试运行时与真实游戏行为分叉。

### InteractiveFrontend

`InteractiveFrontend` 保留当前 GLUT 窗口、键鼠回调、渲染、音频和真实时间循环。GLUT 回调将输入转换成统一游戏动作，再交给 `GameRuntime` 执行。

未传入自动化参数时，游戏行为与当前版本保持一致。

### AutomationFrontend

显式传入 `--automation` 时启用 `AutomationFrontend`。启动形式为：

```bash
Billiards --automation --transport stdio --headless
Billiards --automation --transport stdio --rendered
```

在 `headless` 模式中，不创建窗口、不初始化 OpenGL 渲染资源、不启动音频，游戏时间完全由命令推进。

在 `rendered` 模式中，创建真实 OpenGL 窗口并允许刷新画面和截图，但渲染循环不得自行推进物理时间。

### AutomationController

`AutomationController` 解析和校验协议消息，把命令映射为统一游戏动作、时间控制、查询或测试专用场景修改。它不直接读写终端、Socket 或 OpenGL。

测试专用场景修改只能在自动化模式使用，不出现在普通玩家输入路径中。

### Transport

`Transport` 提供逐条接收请求和发送响应/事件的抽象。首期实现 `StdioTransport`，每行承载一个完整 JSON 对象。

后续传输实现必须复用相同的消息模型和 `AutomationController`，不得在传输适配器中实现游戏规则。

### StateSerializer

`StateSerializer` 将内部状态转换为稳定、版本化的 JSON 数据，客户端不得依赖 C++ 结构体内存布局。序列化字段的删除或语义变更需要提升协议主版本。

## 协议

### 消息格式

每条请求包含：

```json
{"id": 1, "version": 1, "command": "get_state", "params": {}}
```

成功响应复用请求 ID：

```json
{"id": 1, "ok": true, "result": {}}
```

失败响应包含稳定错误码：

```json
{"id": 1, "ok": false, "error": {"code": "invalid_argument", "message": "ball index must be between 0 and 15"}}
```

进程启动成功后首先输出 `ready` 事件，其中包含协议版本、运行模式和能力列表。异步事件包含单调递增的 `sequence` 和当前 `tick`，不使用请求 ID。

### 生命周期命令

- `ping`：检查进程可用性。
- `get_capabilities`：返回协议版本、模式和支持的命令。
- `reset_game`：恢复标准开局状态，并把 tick 重置为零。
- `quit`：完成响应输出后正常结束进程。

### 原始输入命令

- `key_down`、`key_up`：普通键盘输入。
- `special_key`：方向键等 GLUT 特殊键。
- `mouse_move`：鼠标移动或拖动。
- `mouse_button`：鼠标按下和释放。
- `mouse_wheel`：滚轮输入。
- `resize`：窗口尺寸变化。

原始输入必须经过与交互前端相同的动作映射逻辑。对于当前游戏只在单一回调处理、没有独立释放语义的按键，`key_down` 触发现有按键动作，`key_up` 被接受并记录但不重复触发动作。

### 语义操作命令

- `toggle_aim`
- `set_aim_yaw`
- `set_shot_power`
- `shoot`
- `toggle_help`
- `orbit_camera`
- `pan_camera`
- `zoom_camera`

语义操作复用 `GameRuntime` 的动作和规则路径，不允许直接伪造动作的最终结果。例如 `shoot` 设置击球请求并调用正常击球逻辑，而不是直接给目标球写入任意速度。

### 时间控制命令

- `step`：推进指定个数的固定物理 tick，并返回结束 tick、事件摘要和运动状态。
- `run_until`：逐 tick 推进，直到球全部停止、指定事件出现或达到 `max_steps`。

`run_until` 未提供 `max_steps` 时使用协议规定的有限默认值。达到上限仍未满足条件时返回 `condition_not_met`，并附带当前 tick 和最终状态摘要。

### 测试专用命令

- `load_scenario`：原子加载完整测试场景。
- `set_ball`：设置指定球的位置、速度、旋转和落袋状态。
- `set_player_state`：设置当前玩家、球组分配、犯规和击球阶段状态。
- `clear_events`：清除当前已记录事件。

场景修改必须校验球编号、有限浮点数、坐标范围和枚举值。`load_scenario` 在完整校验成功后一次性替换状态；校验失败时不得留下部分修改。

### 查询与产物命令

- `get_state`：返回完整可观察游戏状态。
- `get_events`：返回指定 sequence 之后的事件。
- `screenshot`：在 rendered 模式渲染当前 tick 并保存 PPM；headless 模式返回 `unsupported_in_mode`。

状态快照包括全部球的位置、速度、速度标量、旋转、落袋状态，以及瞄准模式与角度、击球力度、玩家状态、摄像机、HUD、游戏结束状态、球是否运动和当前 tick。浮点值作为 JSON number 输出，客户端断言自行指定容差。

## 执行模型

### 确定性

自动化模式使用命令驱动时间。除 `step`、`run_until` 或协议明确规定包含推进的命令外，任何命令都不得改变物理 tick。

每个 tick 使用项目统一的固定时间步长。相同构建版本、初始场景和命令序列必须产生相同状态与事件序列。

rendered 模式可以在 GLUT 循环中刷新窗口，但刷新不得隐式推进物理。截图必须对应命令处理完成后的确定 tick。

普通交互模式继续使用真实时间累计器驱动固定步长更新。

### 命令顺序

单条命令严格按以下顺序处理：

1. 解析 JSON。
2. 校验协议版本和字段。
3. 校验模式和命令权限。
4. 执行动作或状态修改。
5. 按命令要求推进时间。
6. 收集并编号事件。
7. 按需渲染或截图。
8. 生成响应。

同一传输连接中的请求按输入顺序串行执行。首期协议不提供并行命令执行。

## 错误处理

未知命令、字段类型错误、缺失字段、球编号越界、非有限浮点数、非法状态转换、模式不支持和等待条件超限均返回机器可读错误，不终止进程。

无法解析的 JSON 返回不带请求 ID 的 `parse_error`，随后继续读取下一行。重复请求 ID 不影响执行，但响应仍只与当前请求对应；请求 ID 的唯一性由客户端负责。

只有初始化失败、传输不可恢复地断开或内部不变量被破坏时，自动化进程才以非零状态退出，并向标准错误输出诊断信息。协议 JSON 只写标准输出，日志只写标准错误，避免污染消息流。

## 测试策略

### C++ 单元测试

覆盖以下行为：

- 请求解析、版本和字段校验。
- 每类原始输入与语义操作的动作映射。
- 状态序列化的稳定字段和数值。
- `step` 的固定 tick 推进。
- `run_until` 的成功和超限行为。
- 场景加载的原子性和非法输入恢复。
- JSON 解析错误后继续处理下一请求。
- rendered/headless 模式能力限制。

### 进程级无头 E2E

CTest 启动真实 `Billiards --automation --transport stdio --headless` 子进程，通过管道完成 ready 握手、场景注入、操作、推进、状态/事件断言和 quit。默认 `./scripts/check.sh` 必须执行这些测试。

物理场景至少覆盖：

- 标准开球。
- 球与球碰撞。
- 球与库边碰撞。
- 普通球落袋。
- 母球落袋。
- 球在摩擦作用下停止。

### 渲染 E2E

独立 CTest 标签启动 rendered 自动化模式，执行进入瞄准、调整方向、调整力度、击球、推进物理和截图，并验证截图存在且包含可见像素。该标签只在具备图形环境时显式运行，不阻塞纯无头环境。

### Python 标准驱动器

提供一个只依赖 Python 标准库的客户端，封装：

- 子进程启动和 ready 握手。
- 自动分配请求 ID。
- 请求超时。
- 响应与异步事件分流。
- 常用命令方法。
- 上下文管理器式退出和异常清理。

示例测试不得要求调用者手写 JSONL 或自行管理进程管道。

## 文档与兼容性

用户文档包含启动参数、消息格式、全部命令、状态字段、事件、错误码、Python 示例和传输扩展方式。

协议版本从 `1` 开始。新增可选字段或新命令可以保持同一主版本；删除字段、修改字段类型或改变既有命令语义必须提升主版本。`get_capabilities` 是客户端进行能力协商的唯一依据。

## 验收标准

- 测试程序可从零启动无头或 rendered 游戏进程并等待 ready。
- 可执行所有当前玩家能够执行的键盘、鼠标、滚轮、摄像机、HUD、瞄准和击球操作。
- 可使用测试专用命令构造任意合法球局状态。
- 可按固定 tick 推进，或有限等待某事件/球停止。
- 可读取完整状态和有序事件，并在 rendered 模式生成确定 tick 的截图。
- 无效请求返回结构化错误，进程仍能处理后续请求。
- stdio 传输实现不包含游戏规则，未来 Socket 传输可复用相同控制器和协议。
- 无头 E2E 纳入默认验证入口，渲染 E2E 可在具备图形环境时单独运行。
- 普通交互启动方式和玩家体验保持不变。
